# План тестирования — Premium Notifications Lab

## Что проверяем

**REST API**: `GET /health`, `POST /jobs`, `GET /jobs/{id}`.
**Интеграции**: отправка сообщения в RabbitMQ → обработка worker → `done` в SQLite.
**Нагрузку**: время отклика, RPS, количество ошибок, поведение при увеличении виртуальных пользователей.

## Позитивные сценарии

1. Создание задачи с непустым сообщением → `202`, уникальный `id`, статус `queued`.
2. Получение существующей задачи по `id` → `200`.
3. Worker забирает сообщение из RabbitMQ и меняет статус на `done`.
4. `GET /health` → `200`.

## Негативные сценарии

1. Пустой `message` → `422`.
2. Отсутствует `message` → `422`.
3. `message` длиннее 512 символов → `422`.
4. Неизвестный идентификатор → `404`.
5. RabbitMQ недоступен → `503`, задача отмечается `failed`.

## Нагрузочный эксперимент (Locust)

- Базовая проверка: 5 пользователей, 1 пользователь/сек, 1 минута.
- Умеренная нагрузка: 10 пользователей, 2 пользователя/сек, 1 минута.
- Записать из интерфейса Locust: RPS, p95 времени отклика, failure rate.
- Сопоставить результаты, исследовать нестабильные запросы и ограничения локальной среды.

Это **план испытаний**, а не заявление о полученных результатах.

## Известные ограничения

- SQLite и открытие RabbitMQ-соединения на каждый POST выбраны для учебного стенда, не для production.
- Нет TLS, аутентификации API и производственной обработки повторных сообщений.
- Демонстрационные учётные данные RabbitMQ разрешены только в изолированной локальной среде.
